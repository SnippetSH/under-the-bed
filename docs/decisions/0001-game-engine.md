# ADR-0001: 게임 엔진으로 Godot 4 채택

- 상태: 승인 (2026-11-18)
- 날짜: 2026-11-18

## 맥락

계획서는 엔진 최종 선택(Godot 또는 Unity)을 M6 전까지 미뤄 두었어요. 하지만 두 가지 이유로 지금 정하는 편이 나아요.

- 계획서상 M2 이후부터 "코어 상태를 그리기만 하는 뷰어"를 병행할 수 있는데, 뷰어를 만들려면 엔진이 정해져 있어야 해요.
- 코어 공개 API를 C++ 클래스로 둘지, C ABI로 감쌀지가 엔진 선택에 따라 달라져요.

## 결정

- 렌더링, UI, 입력, 세이브 파일 관리는 **Godot 4**로 해요.
- 코어 연결은 **GDExtension(godot-cpp)** 으로 해요. GDExtension도 CMake로 빌드해서 `sim-core` 타깃을 그대로 링크해요. ([ADR-0004](0004-determinism-scope.md) 참고)
- 엔진 쪽 UI 로직은 GDScript로 쓰고, 시뮬레이션 로직은 한 줄도 엔진 쪽에 두지 않아요.
- Godot와 godot-cpp 버전은 뷰어 작업을 시작할 때 그 시점의 최신 4.x 안정판으로 고정하고, 이 ADR에 버전을 덧붙여요.

## 근거

- **C++ 코어와 직접 연결**: GDExtension은 C++ 그대로 바인딩해요. Unity는 C ABI 래퍼와 C# P/Invoke를 거쳐야 해서 경계 코드가 두 겹이 돼요.
- **2D 적합성**: TileMap과 2D 렌더러가 기본 제공되고, 탑다운 타일 게임에 충분해요.
- **에이전트 협업**: `.tscn`과 `.gd`가 사람이 읽을 수 있는 텍스트라서 PR diff를 리뷰할 수 있어요. Unity의 씬·프리팹 YAML은 GUID 참조가 많아 리뷰하기 어려워요.
- **라이선스**: MIT, 로열티와 설치 수 기반 과금이 없어요.

## 결과

- 좋은 점: 엔진과 코어 사이 경계가 얇아요. 뷰어를 일찍 시작할 수 있어요.
- 감수하는 점: godot-cpp API가 Godot 마이너 버전 사이에 바뀔 수 있어서, 엔진 업그레이드 시 바인딩을 손봐야 해요. 엔진 버전을 고정하고 업그레이드는 별도 PR로 해요.
- 코어 API는 엔진 타입(`Variant`, `String` 등)을 쓰지 않는 순수 C++로 유지해요. 나중에 다른 엔진이 필요해지면 그때 C ABI 래퍼를 추가할 수 있어요.

## 검토한 대안

- **Unity**: 생태계와 에셋은 풍부하지만, C# ↔ C++ 경계 비용, 씬 파일 리뷰 난이도, 과거 라이선스 정책 변경 이력 때문에 제외했어요.
- **raylib/SDL로 직접 구현**: 렌더링은 간단하지만 그래프 패널, 영농일지, 오버레이 같은 UI를 직접 만들어야 해서 비용이 커요.
- **Bevy 등 Rust 엔진**: C++ 코어와 언어가 맞지 않아요.

**버전 고정 (2026-11-20, [ADR-0015](0015-godot-version-and-gdextension-build.md))**: Godot 4.7.2 안정판(표준 빌드), godot-cpp 10.0.0-stable(`GODOTCPP_API_VERSION=4.7`).
